# 架构与协议边界

## 三层架构

ACLIP 的上位归属是 OWorker Open System -> Agent-Native Service Standard (ANSS)。它是 ANSS 下的 CLI/SDK/协议组件，不是 OWorker 平台私有功能。

ACLIP 维护时按三层看：

- 协议契约层：`schema/` 是机器可读事实源。
- 参考 SDK 层：`sdk/python` 和 `sdk/typescript` 是协议语义的双实现。
- 构建导出层：packaging、manifest、Skill export、demo CLI 证明 SDK 能进入真实分发生态。

public 文档只回答“怎么用”。本页回答“维护时怎么判断边界”。

## 事实源顺序

协议语义冲突时按这个顺序处理：

1. `schema/` 的机器契约。
2. `docs/internal/` 的维护决策。
3. Python 与 TypeScript SDK 实现。
4. public 使用文档。

如果实现与 schema 冲突，不能只改文档掩盖；需要同步 schema、SDK、测试和 public 参考。

## ACLIP core 的边界

进入 core：

- 命令树声明。
- 参数声明。
- runtime help payload。
- manifest。
- credential 声明。
- auth/doctor 可选控制面。
- error envelope。
- packaging helper。
- Skill hook/export。

不进入 core：

- 长期 live session。
- REPL。
- 浏览器控制。
- 多 Agent 编排。
- 服务发现排名。
- 从任意 CLI 自动逆向生成完整协议。

这些能力可以在 OWorker 上层生态或相邻工具实现，但不应污染 ACLIP SDK 的稳定边界。

## 包名和协议名

公开包名：

- npm: `@oworker/aclip`
- PyPI: `oworker-aclip`

协议名和代码命名空间保留：

- protocol: `aclip/0.1`
- Python import path: `aclip`

这是为了避免把协议资产改成品牌私有名，也避免破坏既有 Python 代码。
